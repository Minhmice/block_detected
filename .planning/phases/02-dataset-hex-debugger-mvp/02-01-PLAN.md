<threat_model>
Assets: trustworthy detector evidence, bounded Pi/CPU memory and runtime, local dataset/model/config files, and predictable output paths.
Trust boundaries: CLI paths and JSON config are user-controlled; images may be corrupt or huge; `.pt` model loading executes a trusted local serialization format; debug payloads contain NumPy and custom objects.
Threats and mitigations:
- HIGH config/state corruption: accept only keys returned by `dataclasses.fields(HexDetectorConfig)`, require a JSON object, call `HexDetectorConfig(**values).validate()`, never use `importlib`, and retain last valid state after R failure.
- HIGH evidence divergence: never rerun CV stages in the script; capture intermediates in the actual detector pass and regression-test Phase 1 behavior.
- MEDIUM CPU/memory amplification: load one image at a time, create one detector per processing pass, bound candidate summaries with `debug_top_candidates`, store heavy edges only in verbose state, and release previous-image state during navigation.
- MEDIUM unsafe output naming/path collisions: derive filenames from sanitized source stems, create only the four documented output locations, and use deterministic overwrite semantics for reruns.
- MEDIUM arbitrary model risk: load only the explicit local `--model` path supplied by the operator; do not download, discover, or auto-update weights.
- LOW JSON serialization failure: recursively sanitize known dataclasses/containers/NumPy scalars; save edge pixels as PNG rather than embedding large arrays.
Residual risk: OpenCV GUI/key behavior varies by backend; D/A/Q/ESC are mandatory portable controls and arrow support is best-effort across known key codes.
</threat_model>
